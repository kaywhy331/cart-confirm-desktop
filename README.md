# Cart Confirm Desktop

Cart Confirm is a local Windows desktop app and unpacked Chrome companion for a multi-item buy list on Target, Walmart, and Amazon. Each item is one row with Target, Walmart, and Amazon as optional store routes. Shared intent—quantity, action, schedule, fulfillment, and alerts—is configured once for the item, while each selected store keeps its own URL, SKU, price cap, affiliate link, and captured image. An optional official Discord bot connection can ingest restock alerts into a local Desired/New signal inbox.

The companion uses the normal signed-in store pages. It can keep checking an unavailable item, add an eligible offer to the cart, set the configured quantity, and proceed to a capped final review. **Stop at final review** is recommended. **Submit order automatically** is an advanced opt-in that additionally requires an explicit shipping/pickup mode and can select the final order control.

## Safety rules

These rules are enforced in code and cannot be disabled from the UI:

- The URL and exact store identifier must match: Target TCIN, Walmart item ID, or Amazon ASIN.
- The page must expose a readable unit price at or below the product's cap.
- The default seller policy is verifiably first-party: Target, Walmart, or Amazon directly. A Signal strategy can explicitly allow marketplace sellers; that exception remains bound to the exact activation, requires a visible live seller, and requires the same normalized seller when the signal names one. Missing-seller offers still fail closed. Because Target labels marketplace (Target Plus) offers explicitly and shows no seller text for items it sells itself, an unlabeled Target offer is treated as first-party only when no marketplace marker appears anywhere on the page; any marker fails closed. Walmart and Amazon always require an explicit first-party label for first-party classification.
- The requested cart quantity must be confirmed after any quantity change settles.
- Current cart seller and price evidence must be readable; product-page evidence cannot make an ambiguous cart safe.
- Before checkout, the companion must completely enumerate exactly one cart line, independently reconcile remove controls, and prove that it is the configured SKU. Unknown, duplicate, and extra lines block submission.
- Checkout requires fresh cart-confirmed proof and a readable final order total at or below that row's positive final-total cap. Auto-submit captures a fresh visible final-review snapshot whose keyed HMAC fingerprints cover the destination or pickup store, complete selected payment-instrument set, substitution state, single cart line, quantity, SKU, fulfillment, and total. An advance preflight is optional—use it when an item is available to lock those hashes ahead of time; if one exists, the live checkout must match it exactly. Sold-out and unreleased missions can arm without one, but the same complete live evidence must validate immediately before submission. The readable address/payment labels never leave transient content-script memory and are never persisted.
- Each product is processed by exactly one tab — duplicate tabs cannot claim the same product — and **Add to cart only** items run in parallel across their own tabs. Every add gets a durable receipt before the click. Walmart and Amazon remain single-flight. A calendar-fired Target mission gets a bounded persistence burst (20 seconds per stage and 750 ms between persistence actions by default): an explicit Target error dialog may be dismissed and retried, and a fully loaded cart that proves the exact TCIN absent may reopen Add; an ambiguous response goes to exact-cart verification instead of blindly adding again. Unscheduled Target watchers never enter that rapid lane. Final-review and auto-submit workflows remain exclusive per store: only one purchase flow per store at a time.
- A qualified purchase mission immediately leaves its stock-refresh lane and reports **Processing**. The extension atomically claims the exact product/store lane, saves the verified offer proof, and reserves Add; it then obtains the traffic authorization and performs one final Stop/config plus reservation check directly beside the click. A healthy local/store lane is optimized for prompt Add initiation, but retailer network completion is never promised. An abandoned pre-click reservation expires after 15 seconds. Once Add may have been clicked, the lane is held indefinitely until exact cart evidence resolves it; another qualified mission shows an explicit safety notification instead of silently waiting behind that hold.
- After a Target Add click, the companion polls the visible cart count every 75 ms for up to three seconds. An increase opens the cart immediately for exact-TCIN verification; otherwise the three-second fallback opens the cart for the same verification. After cart hydration, a readable zero-item header or complete inventory proving the TCIN absent clears only that failed Add receipt for a bounded retry. Ambiguous cart evidence remains locked for manual review.
- A confirmed product is marked complete for the current automation run and cannot be purchased twice. Disarming and re-arming intentionally starts a new run.
- Store routes selected on the same item are alternatives, not separate purchase goals. They can monitor concurrently, but only the first route to claim the protected purchase boundary may act; its sibling routes wait and then complete with the item so the same item is not bought from multiple stores in one run.
- Proof, attempts, completion, and submit intent live in extension-owned storage. An uncertain final click holds its run lock until a retailer-specific confirmation or explicit failure appears. The popup offers an operator-only **I checked: no order exists** release after Autopilot is fully off and the operator has inspected the retailer cart and order history; Cart Confirm never infers that outcome.
- Final auto-submit re-reads the complete evidence immediately before clicking, requires the configured shipping/pickup mode, and blocks selected subscriptions, protection plans, tips, donations, gift wrap, and installment choices.
- Desktop launches start fully **STOPPED** by default: Signals and Autopilot are disarmed, browser scans and retries are paused, background checks and schedules cannot fire, and Discord is not polled. The Chrome extension can retain sanitized TrackaLacker pushes while the desktop is closed, but no mission is activated until CartCollect is reopened and Signals is explicitly armed. Starting an edit while either purchase mode is armed pauses the run once and opens a plan-edit session; individual saves stay paused until **Finish editing** deliberately starts one updated run in the same mode.
- A mission with **Open at** remains calendar-owned until the desktop records its firing boundary. Arming Autopilot, an already-open tab, quiet stock checks, Discord signals, and queue fan-out cannot scan, refresh, or act on it early. The desktop durably assigns its blitz execution context before clearing that gate. A missed time remains locked until you clear or reschedule it, so it cannot silently run late.
- Browser observations and Discord messages are untrusted signals, never purchase proof. Signals match missions only by normalized `retailer:SKU`; their price, seller, stock, offer ID, and action links are re-validated before use, and the signed-in retailer page remains authoritative.
- Catalog listing prices and AI research are untrusted hints. TrackaLacker imports are also not live purchase proof: the preview preserves the latest captured store price—including surge and above-MSRP observations—but only the newest same-store history point classified by TrackaLacker as normal/MSRP-like can supply a ready cap. Missing normal history and product-level fallback estimates remain Off for cap review. The signed-in retailer page is still authoritative before any action. Cited research is never applied to MSRP or existing missions automatically.
- Only official Discord bot tokens are accepted. The token is stored separately through Electron's operating-system encryption; plaintext and Linux `basic_text` fallbacks are refused. Discord user tokens and self-bots are not supported.
- A first Discord connection imports recent messages as history without opening pages. Later signals must be under two minutes old to auto-open. **Stop everything** pauses Discord polling as well as automatic openings, so nothing new is ingested until an explicit Arm, Monitor-only, or Open action resumes monitoring.
- CAPTCHAs, queues, sign-in/MFA prompts, location choices, membership/invitation gates, and security challenges are never bypassed. When Walmart places one mission on an official `/qp` queue or an unmistakable product-route waiting room, Cart Confirm makes one exactly-once simultaneous pass through the other enabled Walmart missions so they can enter through their normal product pages too. A tab already in queue is frozen: ticket endpoints and signatures are never stored, called, replayed, or refreshed. Unknown high-demand pages freeze for manual review.
- Every eligible tabless Target/Walmart watcher has its own randomized 45–90 second public-page deadline after an immediate shuffled, paced first ramp. Authenticated open-tab watchers use the configurable 60-second default. Both remain armed until **Stop everything**, disarm, completion, or a fail-closed safety condition. Calendar-fired missions use the separate rapid pre-eligibility lane (two seconds by default).
- Public quiet GETs use a separate fixed 4,000-read rolling-hour ceiling per store plus a persisted 45-second per-product floor. Authenticated browser navigation, cart, checkout, and submission actions retain the unchanged fixed 120-action rolling-hour budget. Explicit overload and security cooldowns are shared by both lanes and always override cadence; a cluster of anonymous transport failures rests only the public-read lane so a healthy authenticated tab can still verify and act.
- Tool-controlled navigations are serialized per store. HTTP `429`, `502`, `503`, `504`, and `520`–`524` responses open an escalating store-specific cooldown circuit, and a bounded `Retry-After` header is honored.

Start with **Add to cart only** until you have verified the current store selectors and your account setup. Store markup changes regularly, so live checkout behavior cannot be guaranteed by the source tests alone.

## Features

- An item-first control list: each item appears once, with compact Target, Walmart, and Amazon toggles beneath it. A validated retailer-hosted image captured by Quick add or the first observed store page appears before the store options; hovering the row or focusing its thumbnail opens a medium preview. Price differences appear as a range, and each selected store has its own direct **Open** action. Use drag-and-drop or the accessible up/down arrows to reorder items. Search and filter by group, retailer, On/Off state, or **Needs attention**; group headers can collapse, rename, or turn every member On/Off.
- Automatic update discovery for packaged 64-bit Windows builds. The top bar stays quiet when the app is current and shows **vX.Y.Z available · Update** only for a newer release. **Update** presents the release notes before approval, then requires the exact versioned Setup asset and `SHA256SUMS.txt`, verifies the download's size and SHA-256, pauses automation, installs, and relaunches. Intentionally unsigned prereleases retain their Windows Unknown publisher / SmartScreen warning.
- Up to 100 logical items and 100 selected store routes across Target, Walmart, and Amazon. A three-store item counts as one item and three store routes; the route ceiling keeps the existing page-opening and traffic safety boundary intact.
- A centralized **Item defaults** panel with reusable item profiles and per-store MSRP by stable product type. New installs default to quantity 1, shipping, standard alert, and **Watch & alert only**. Existing saved default selections are preserved, and the legacy shipping auto-buy profile remains available only as an explicit choice. New items without a positive approved cap remain Off.
- A focused **Edit plan** session. It pauses an active run once, adds selection controls directly to the filtered item rows, and groups template, On/Off, group, shared-time, clear-time, copy-list, and explicit **Combine stores** actions beside the list. **Undo** and **Revert plan** make multi-step edits recoverable before **Finish editing** starts one updated run.
- A persistent run-state banner that distinguishes **Stopped**, **Monitoring only**, **Signals listening**, and **Autopilot active**. **Review & start** opens a structured preflight with item counts, scheduled work, action mix, maximum exposure, blockers, and warnings before the user chooses monitoring, event-driven Signals, or continuous Autopilot.
- A distinct **Signals** mode that does not start a broad mission sweep. A fresh exact TrackaLacker, browser, or Discord match creates a ten-minute, in-memory authorization for only that `retailer:SKU` in the current run. The companion receives every unrelated mission as disabled, while the matched page must still re-prove the live signal and mission price caps, strategy seller policy, quantity, fulfillment, complete cart, final total, and checkout evidence before any action.
- Ordered, user-managed **Signal strategies** shared by TrackaLacker, browser, and Discord inputs. Each strategy can select a cumulative MSRP cap, current mission stores, first-party-only or explicit third-party seller policy, include/exclude keyword expression, Notify/Add To Cart/Prepare Checkout/Submit Order action, and quantity 1–5 or **Max Allowed** up to the mission cap. The first enabled match wins; a visible catchall warning helps keep broad defaults at the bottom.
- Starter Pokémon MSRP rows for ETB, blister pack, single booster pack, SPC, and UPC. Their store prices intentionally begin blank: Cart Confirm does not ship guessed prices. Approve each stable category once for Target, Walmart, and Amazon instead of typing a price on every mission.
- Optional monthly MSRP research through the OpenAI Responses API `web_search` tool. The API key is encrypted by the operating system and automatic 30-day research is a separate opt-in. Results retain visible, clickable citations and remain suggestions until **Accept MSRP** is selected. See the [official OpenAI web-search documentation](https://developers.openai.com/api/docs/guides/tools-web-search).
- A Chrome-toolbar **Quick add** popup that reads the exact TCIN / Walmart item ID / ASIN, retailer title, current price, and product-image reference from the open product page. The positive observed price becomes the cap; the default item profile fills quantity, shipping, action, and alert, while the tax and retailer settings supply the final-total cushion. Existing duplicates keep all purchase settings while newly captured affiliate-link and thumbnail metadata may be attached; a missing/non-positive price is refused.
- A desktop **Import links** dialog for pasted Target, Walmart, and Amazon product URLs. It extracts and normalizes item IDs, strips tracking parameters, skips duplicates, and applies the default item template. A preview reports ready, unpriced, invalid, duplicate, and over-capacity rows without changing the plan; only **Confirm import** saves them. An approved title/store MSRP match can make an item ready, while an unknown price stays Off at a $0 cap.
- A user-triggered **Catalog Inbox** for keyword discovery. It opens one official Target, Walmart, or Amazon search page per selected retailer and catalogs up to 20 visible result cards from each page with exact item ID, title, canonical URL, displayed listing price, retailer, and observation time. Optional include/exclude-word and maximum displayed-price filters run locally; selected results use the chosen item profile and approved MSRP rather than trusting displayed listing prices.
- A product-first **TrackaLacker followed-products** importer. The companion uses the already signed-in TrackaLacker browser session—never a password supplied to Cart Confirm—to read bounded followed pages and up to 50 newest listing-history observations sequentially. The preview shows one product with its thumbnail, TrackaLacker source, supported Target/Walmart/Amazon store toggles, exact store routes, newest normal cap, latest price, low/high range, trend, surge state, expandable history, and future-store labels. Selected store options import under one shared item ID instead of becoming item+store duplicates.
- Plain-language speed and traffic settings with **Recommended**, **Low traffic**, and **Scheduled drop** setups, plus up to 12 named custom setups saved locally. A setup stores only timing, traffic, and fast-load values—never missions, caps, quantities, actions, credentials, or Autopilot state.
- Per-product maximum unit price, quantity, fulfillment mode, enabled state, and a mission action: **Watch & alert only** (monitors and alerts at or under your cap without ever clicking), add-only, final-review, or auto-submit. The final-order cap is read-only and recalculates as `item subtotal + configured tax + retailer allowance`; tax defaults to 12% and each retailer allowance defaults to $30. Rarely used fields live behind each row's **Advanced** section.
- Per-product alert loudness: standard ping, **loud alarm** (repeating audible alert with an on-screen Silence bar, throttled to once per five minutes per item), or silent milestones. A silent mission records a safety-stop notification in Activity without producing an operating-system popup, so `! Blocked` never has to be diagnosed without a reason.
- A worst-case exposure line and readiness metric: the total if every enabled item hits its cap — automation can never exceed the caps you set.
- Click any live-status row to filter the event log to that item's timeline.
- A **Monitor only** button in the header that connects the Chrome companion automatically, then opens every enabled mission without a calendar time through the paced per-store queue while Autopilot is off, so the companion can report price, seller, and stock without touching the cart. Scheduled missions remain closed until their exact time.
- Background-first stock checks for unscheduled Target and Walmart missions. Every eligible tabless product joins an immediate shuffled ramp with request starts paced at least 500 ms globally and 750 ms per retailer; after each start, that product receives a fresh randomized 45–90 second deadline. Public reads have no cookies or cart access and use a separate fixed 4,000/hour/store guard. If Chrome is not connected when Autopilot starts, Cart Confirm opens one mission page and waits for its authenticated companion heartbeat; watcher missions open after a likely stock signal, or immediately after their first check when the public page loads without readable stock data (Target renders availability only inside a real browser session). Amazon remains tab-based.
- Scheduled openings for known drop times: give an item one shared **Open at** date/time, save, and start the run in advance. Until that boundary, even an already-open store route stays idle. The agenda groups equal times into cohorts, shows the explicit local timezone and simultaneous-item count, and provides direct edit, On/Off, and missed-time recovery actions. Due Walmart routes still launch simultaneously in dedicated tabs (or immediately reuse their exact tabs); other same-store drops retain the bounded drop lane.
- Official-queue fan-out for simultaneous Walmart drops: the first enabled mission that reports a live `/qp` queue or a conservatively recognized Walmart waiting room causes every other enabled, not-yet-queued Walmart mission to navigate once at the same time. For calendar-fired Walmart blitz missions, that first nonsold-out queue report also freezes the winner and immediately signals every other Walmart tab. Each nonqueued blitz tab is allowed to settle for two seconds; final queue-capture reloads default to **0** (disabled) and can be explicitly configured from 0–20. A tab freezes immediately if a queue appears and stops permanently at the configured cap. A durable per-run receipt prevents a second burst, Stop cancels pending pages, and every navigation still consumes the shared traffic budget.
- Official Discord bot ingestion with a local Desired/New signal inbox, stable store+SKU matching, encrypted credentials, silent history import, and per-mission auto-open controls. Fresh same-store signals enter the one-second drop lane while different retailers proceed independently.
- Admin/backend-provisioned Howl campaign links. The normal mission editor never asks for or resolves a Howl URL. A trusted admin workflow can resolve a generated link for an exact mission, after which the operator can copy only its validated retailer-domain sharing URL from the mission or a matching Discord signal. Campaign links remain sharing-only and never enter the purchasing configuration sent to Chrome.
- Sanitized direct signal entries for Amazon Add to Cart / Buy Now and Walmart Buy Now. Amazon requires a fresh under-cap price, `Amazon.com` seller, exact ASIN and whitelisted offer parameters. Walmart constructs only `https://www.walmart.com/affil/cart/buynow?items=<exact item ID>` from the normalized signal SKU (or reduces a supplied button to that form). Tracking parameters are stripped, durable tab context follows redirects, and missing browser context falls back to the canonical product page.
- Manual **Open all due** action for enabled, unscheduled missions across all stores, with each store's pages queued independently. When the companion is connected, an existing Chrome tab for that store is navigated instead of opening a new window, and identical pending opens are deduplicated.
- Configurable authenticated open-tab watcher interval from 30 to 3,600 seconds (60 seconds by default); tabless Target/Walmart public monitoring uses the independent randomized 45–90 second target.
- Configurable blitz retry interval from 5 to 3,600 seconds and pre-eligibility refresh spacing from 2 to 60 seconds, with jitter/backoff on ordinary blitz errors.
- Configurable Target blitz action delay from 250 to 5,000 ms and per-stage persistence window from 5 to 120 seconds. Fixed per-stage action counts and the rolling store budget remain hard limits.
- Configurable per-store navigation spacing from 10 to 3,600 seconds and overload cooldown from 60 to 86,400 seconds.
- Automatic recovery when an item becomes unavailable in the cart or during checkout.
- Optional fast-load mode that blocks images, fonts, and media while preserving HTML, CSS, JavaScript, authentication, and store controls.
- Per-product offer, seller, unit price, observed final total, cart, checkout, attempt, and confirmation status.
- Windows desktop notifications and a bounded persistent local safety ledger.
- Legacy migration from the original single-product Target settings.

## Background stock checks vs. browser-only purchasing

Arming Autopilot starts unscheduled Target and Walmart watcher missions **background-first**. If the Chrome companion is disconnected, the desktop first opens one relevant mission page in Chrome and waits up to 15 seconds for a fresh authenticated heartbeat; an installed older bundled companion receives one automatic reload/reopen attempt. A failed connection switches Autopilot back off instead of leaving an inert armed run. Once the connection is ready, Activity records one **Watch Started** milestone for every due mission. Every eligible tabless mission enters an immediate shuffled, paced ramp, and every first public read remains ahead of every repeat even if the Chrome bootstrap tab completes several authenticated watcher rounds while that ramp drains. Starts remain at least 500 ms apart globally and 750 ms apart per retailer, with at most four reads globally, two per retailer, and one per product in flight; slow eight-second responses can therefore make a large same-store first ramp visibly gradual without starving later products. After its first start, each product receives its own randomized 45–90 second start-to-start public-page deadline. The fixed public-read guard is 4,000/hour/store and cannot consume the separate 120/hour browser/cart/checkout ledger. Calendar-owned, fired-blitz, completed, and fresh live-tab missions are excluded. Cadence is a target: slow responses, the read ceiling, system sleep, Stop, and retailer cooldowns can delay a check, and delayed checks never create catch-up bursts. When a quiet watcher sees likely availability, it opens the canonical product page in Chrome through the existing browser-action governor; the authenticated in-tab pipeline remains authoritative and re-validates the exact SKU, first-party seller, price cap, quantity, complete cart scope, fulfillment, and final order total before acting. Inactive authenticated tabs keep their first pending DOM scan instead of allowing Target's continuously changing page to postpone it indefinitely, and bringing a tab forward requests an immediate scan. The moment a mission qualifies for a real cart action, the companion switches Chrome back to that exact mission tab and keeps it forward through cart verification and checkout, so background-tab throttling can never stall a time-critical purchase; Watch & alert only and Monitor-only observation never pull focus. It never jumps directly to checkout. A **Stop at final review** mission remains on Target's checkout-review page for the operator. A successful **Submit order automatically** mission remains on Target's confirmation/receipt page after Target confirms the order. No receipt redirect is synthesized. A public page that loads without readable stock data opens its authenticated Chrome watcher after the first check and rests quiet checks for ten minutes; three transient unreadable responses put only that product into the same automatic ten-minute rest with a **retrying** status, not a manual block. An exact open retailer tab uses the authenticated browser watcher in the meantime. Explicit overload/security challenges open the shared store cooldown. Several distinct anonymous transport failures rest only public monitoring, allowing an authenticated Chrome fallback to proceed. Amazon is tab-only. **Stop everything** is a hard cancellation boundary: it aborts active quiet HTTP checks, wakes and cancels store-opening waits, drops late non-health tab events, clears retry timers as the tabs receive the stopped configuration, pauses Discord and scheduled execution, clears active runtime contexts, and disables Fast Mode. Configured mission times and Walmart prep candidates remain saved. Only a connection heartbeat remains. Autopilot, Monitor only, Open, or Open all explicitly resumes monitoring.

Purchasing, by contrast, is browser-only, and deliberately so: authenticated carts and checkout flows depend on browser JavaScript, cookies, CSRF protections, inventory checks, and store security controls. Replaying private requests or treating checkout as a plain HTML form would be fragile and could submit stale or unsafe data.

Fast-load mode keeps the authenticated browser workflow but removes nonessential image, font, and media downloads. If a security challenge appears, resource blocking is paused for ten minutes so the challenge can be completed manually. The blocking rule is removed whenever the desktop companion is unavailable or fails its version/pairing checks.

## Windows quick start

1. Extract this project to a permanent folder.
2. Double-click `RUN-ON-WINDOWS.cmd`.
3. On first launch, the script installs Electron and starts the app.
4. Select **Show companion folder** in Cart Confirm.
5. Open `chrome://extensions` in Chrome.
6. Turn on **Developer mode**.
7. Select **Load unpacked** and choose the shown `extension` folder.
8. If an older companion is already loaded, select **Reload** on its extension card and approve any added first-party or notification permission Chrome displays.
9. Sign in normally to every store you plan to use and verify saved delivery, payment, and store preferences.

When launching from PowerShell instead of double-clicking, include the current-directory prefix:

```powershell
.\RUN-ON-WINDOWS.cmd
```

To update an existing Git checkout, close Cart Confirm first, then run:

```powershell
git pull --ff-only
npm ci --no-fund
.\RUN-ON-WINDOWS.cmd
```

If Chrome still shows `UPD` after the app restarts, reload the unpacked extension once from `chrome://extensions`.

Packaged Windows installs check this repository's official GitHub releases at startup and every six hours. Selecting the always-visible **Check for updates** button performs the same check immediately. When a newer release exists, the top bar shows **vX.Y.Z available · Update**; selecting **Update** displays the patch notes and asks for approval. Cart Confirm never downloads or installs silently. After approval, it verifies the official GitHub release checksum, pauses automation, installs the desktop app and matching bundled extension files together, and relaunches. The already-loaded unpacked companion performs one bounded reload from that updated folder. Chrome can require one approval when a release adds an extension permission; approve the **Cart Confirm Companion** card in `chrome://extensions` if prompted. Source-checkout development runs continue to use the Git commands above.

The extension badge reads `STOP` when monitoring is paused, `IDLE` when monitoring is active without a purchase mode, `SIG` while Signals is listening or processing an exact match, and `ARM` when Autopilot is armed. Keep the desktop app open while running the buy list.

## Configure a buy list

Click **+ Add item**, then:

1. Turn on each store where the item should be watched. Pick a store's **Edit** control and paste its product-page URL. Cart Confirm detects that store's TCIN / Walmart item ID / ASIN and keeps the store-specific route fields together. At least one store must remain selected.
2. Enter the item name once. Quantity, action, schedule, fulfillment, alert, group, template, and the item-level On/Off control are shared by every selected store; URL, SKU, unit cap, MSRP evidence, affiliate link, image, and signal entry remain store-specific.
3. Cart Confirm applies the selected item template and any matching approved store MSRP. New installs default to quantity 1, **Shipping / delivery**, and **Watch & alert only**; an existing saved default remains unchanged. A store route without an approved positive cap remains Off for purchase actions until you enter one or approve the product type under **Item defaults**.
4. The app calculates each store route's maximum final order total from `item subtotal + configured tax + that retailer's saved allowance`. The global tax estimate defaults to 12% and each store allowance defaults to $30; adjust both under **Item defaults** for your location and expected shipping or fees.
5. For auto-submit, a positive unit cap, sufficient positive final-total cap, and explicit shipping/pickup requirement are mandatory. Advance checkout preflight is optional so sold-out or unreleased items can arm. When stock appears, the live final-review page must still prove the destination/store, complete payment set, disabled substitutions, exact single cart line, quantity, SKU, authorized seller policy, fulfillment, and capped total; that evidence is checked again immediately before the click.
6. Optionally add each store's **Affiliate product link** and signal-entry preference under **Advanced**. Affiliate links must be direct HTTPS URLs for that route's exact store and item ID. Manual **Open** prefers the affiliate route; watchers, schedules, signals, and purchase automation always use the canonical product URL.
7. Click **Done** to save every selected store route atomically. During a run, the first selected store to reach the protected purchase boundary claims the item; the other stores cannot buy a duplicate. Starting an edit while Autopilot is on pauses it once and joins the plan-edit session.

### Quick add from Chrome

With the desktop app connected and Autopilot off, open a supported retailer product page and select the Cart Confirm toolbar icon. The popup previews the detected store, exact item ID, retailer title, current page price, availability, and visible seller. Select **Add with default profile** to append it to Missions. The observed positive price becomes its unit cap and the current default item profile supplies the remaining fields. On a new install, that means shipping + watch-only. Autopilot is still Off and must be armed separately; all purchase evidence is re-validated in the browser.

Quick add does not overwrite an existing mission or its cap. It also stays disabled if the page has not exposed a finite positive price, if the desktop app is unavailable, or while Autopilot is armed. Refresh the retailer page or the popup after dynamic page content finishes loading. Use the top-right ×, the smaller × beside **Add with default profile**, Escape, or click anywhere outside the popup to close it without adding.

### Bulk import product URLs

In the desktop app, select **Import links**, paste supported Target, Walmart, or Amazon product links, and select **Preview import**. Links can be on separate lines or separated by spaces. Cart Confirm detects each TCIN / Walmart item ID / ASIN, converts it to a clean canonical product URL, removes duplicates already in the plan or in the pasted list, and reports invalid or over-capacity entries. Review the counts, then select **Confirm import**; previewing never changes the item list.

Bulk import does not contact retailer pages or trust a visible listing price. It applies the default item profile and matches the URL-derived title against the approved store MSRP table. Matching rows receive that approved cap; unknown rows remain Off with a $0 cap. Opening Bulk import during a run pauses Autopilot once and joins the same plan-edit session, so imported missions can be reviewed before **Finish editing** starts the updated run.

### TrackaLacker followed-products import

With Autopilot off and Cart Confirm Companion loaded, open **TrackaLacker** from the Items toolbar and choose **Scan followed products**. Cart Confirm opens `https://www.trackalacker.com/products/followed` in the companion browser. Sign in there if needed and leave the tab open. The extension claims one scan tab, discovers up to 500 followed products over at most 50 pages, and processes product details and supported listing histories sequentially with bounded retries. Cancel stops further reads while retaining the products already captured; **Scan again** safely replaces the preview and can resume after a failure.

The preview is item-first. One TrackaLacker product card owns its Target, Walmart, and Amazon checkboxes. Duplicate listings for one retailer are reduced to one exact product route, with a concrete product page preferred over a search result; alternate counts remain visible. Retailers the automation does not yet support are named for future support but cannot become missions. The TrackaLacker product, exact store route, and listing-history links are clickable before import, and the TrackaLacker thumbnail becomes the mission thumbnail and hover preview afterward.

Each listing’s available history (currently up to 50 newest observations supplied by TrackaLacker) is normalized newest-first and saved locally. Surge and above-MSRP points remain in the history so the preview can show the real latest price, full low/high range, direction of the latest distinct price change, and spike warnings. They cannot become caps: the newest normal/MSRP-like point is the store’s proposed cap. If the latest price is a surge, the preview shows both that latest surge and the older normal reference date instead of making the spike look like the expected price. If no normal store point exists, the followed-product estimate is retained for convenience but the store option stays Off for review.

Expand **Price history** under a store option to load its saved points and trend chart. Full histories are fetched only for the expanded vendor; routine desktop updates and mission settings carry a compact summary so large followed lists remain responsive. Imported mission rows use the newest exact-listing summary available—latest, range, trend, and surge state—without sending history records to browser automation. A new scan replaces the locally captured preview and refreshes those mission-row facts, but it never silently changes a saved purchase cap; a changed normal reference is shown beside the unchanged cap for review. Import never changes existing routes, and the 100-store-option plan limit still applies.

The scan uses only the browser’s existing TrackaLacker cookies. Cart Confirm does not ask for, transmit, log, or persist TrackaLacker credentials. Product preview data is stored locally in `trackalacker-import.json`; it contains normalized product/listing identifiers, source/history URLs, image URL, bounded price histories and summaries, status, and timestamps—not cookies or passwords.

## Admin/backend Howl campaign provisioning

const { provisionHowlCampaign } = require("./lib/admin-campaigns");

That backend call deliberately performs the GET redirect chain that can register the Howl click. ## Use Signals mode

Choose **Review & start → Start Signals** when external restock events should drive the run. Signals and Autopilot are mutually exclusive. Signals does not open every due mission, run tabless quiet watchers, fire calendar work, or enable combined checkout. Enabled missions remain dormant until one of these exact inputs arrives:

- The bundled Chrome extension receives TrackaLacker Web Push, then resolves the sanitized notification title + retailer against the last complete TrackaLacker pre-sync snapshot. Unknown or ambiguous variants remain in the audit as unresolved and never select a mission.
- The companion observes a live offer on an already-open Target, Walmart, or Amazon product page. The desktop records it as a **Browser** signal and applies the winning strategy's seller policy before authorizing only that exact mission.
- The connected official Discord bot receives a live restock message that parses to one supported store and normalized SKU. Historical, stale, unmatched, disabled, calendar-owned, and quantity-limit-conflicting messages remain recorded without purchase authority.

The run review now gives a concrete setup path instead of an inert `0 / N` summary. Turn on at least one intended item (Watch-only items do not require a purchase price cap), then make at least one source ready: choose **Connect one page** for browser observations, enroll and scan TrackaLacker Push, or connect the official Discord bot. Choose **Configure signals** to add ordered rules; **Add safe Notify catchall** creates a non-navigating default when you do not need keyword filtering yet. The review blocks **Start Signals** until an item and a real source are ready, and it lists configured sources that need repair.

An authorization exists only in memory, is tied to the current run ID, and expires after ten minutes. It is not a purchase approval: Signals always enters through the canonical product page, then the signed-in store page re-reads the offer before reservation and again immediately before Add to cart. The live price must be no higher than both the mission cap and the signal price. The seller must be first-party unless the winning strategy explicitly allows third parties; a named marketplace seller must still match. The same binding continues through cart and checkout validation alongside configured quantity, fulfillment, complete cart contents, final order-total cap, and checkout evidence. A mismatch cancels only that signal without clicking Add, so a later legitimate restock signal can activate the mission again. Item/store locks and durable submit intent still prevent sibling-store duplicates and uncertain resubmission. Turning Signals off, switching modes, choosing **Stop everything**, restarting, editing the plan, or installing an update clears every activation.

### Configure signal strategies

Open **Restock signals → Signal strategies** while Signals and Autopilot are off. Add as many as 25 rules, then use the up/down controls to set priority. Rules are evaluated from top to bottom and processing stops on the first enabled rule whose store, price band, include query, and exclusion query all match. Edit and Delete change only the selected rule. If the list is empty, the existing per-mission signal action remains in effect for backward compatibility. Once at least one strategy exists, an exact mission signal that matches no enabled strategy is recorded without taking action.

Store checkboxes are generated from the Target, Walmart, and Amazon options currently present in Missions; leaving them all clear means any available store. An empty include query is a catchall. Inside a query, spaces or `+` mean AND, `|`, comma, or `OR` separates alternatives, matching single or double quotes require an exact phrase, and `-term` is an inline exclusion. The separate exclusion field uses the same clauses and rejects the rule when any clause matches. For example, `pokemon + "elite trainer box" | 'booster bundle'` matches either the required Pokémon phrase pair or the exact booster-bundle phrase, while `used | refurbished | "open box"` excludes those conditions.

TrackaLacker's own MSRP classification is used when its push supplies one: below MSRP, MSRP/source-labeled near MSRP, explicitly slightly above MSRP, and above MSRP/price surge. For browser or Discord prices with an approved per-store MSRP, the exact approved amount is **MSRP**, up to 10% higher is **Slightly above**, and anything higher is **Above**; a price-specific rule does not match when no classification can be proven. These selections are cumulative caps: **At or below MSRP** also matches below-MSRP signals, and **Up to 10% above MSRP** also matches MSRP and below. **Notify** creates a local notification without opening a store. The three purchase-capable actions create only a short-lived exact-mission activation. **Allow third-party sellers** is off by default and applies only to that strategy. Each strategy row previews the effective authorization across enabled routes. Its action and quantity can narrow, but never exceed, the matched mission's configured action and quantity; the mission's price, seller, fulfillment, total, checkout-evidence, lock, and traffic safeguards remain authoritative.

### TrackaLacker Chrome push bridge

Chrome 121 or newer can receive silent Web Push in the bundled Manifest V3 extension. In **Restock signals**, enable the bridge and choose **Connect TrackaLacker push**. Cart Confirm immediately opens TrackaLacker's notification-settings page in Chrome; keep it signed in while the companion creates its real `PushSubscription` and enrolls it as **Desktop - Windows - Chrome** through TrackaLacker's same-origin `POST /api/v1/users/devices` request. The desktop waits for a correlated ready/error receipt, so opening a page alone is never reported as success. **Recheck** migrates an older visible companion endpoint through TrackaLacker's own `PATCH /api/v1/users/devices/update_token` rotation contract while preserving its discreet nickname. The operation reuses the page's current cookies and CSRF state. CartCollect never asks for or stores a TrackaLacker username, password, cookie, subscription endpoint, `p256dh`, or `auth` value.

The extension checks whether TrackaLacker's page-owned push subscription exists but never replaces, unregisters, or exports it. That normal browser location remains the one visible Windows popup. The separate extension subscription uses TrackaLacker's public Web Push application key silently, so leaving both TrackaLacker device rows enabled does not create a second companion popup. Only a SHA-256 endpoint fingerprint is retained to avoid background re-enrollment; an explicit **Connect/Recheck** deliberately repairs or rotates the endpoint when needed, with an already-enrolled response treated as ready. There is no recurring TrackaLacker registration or product poll.

Live TrackaLacker messages may state the event as `<product> is in stock at <store>` instead of putting the product on a standalone line. CartCollect normalizes that bounded sentence before exact matching. When the visible notification text omits the product, the extension may derive only an exact public TrackaLacker product slug, numeric followed-product/listing identifier, or validated Target TCIN, Walmart item ID, or Amazon ASIN from the click destination. The full URL, signed notification identifier, query string, and campaign fields are discarded before the push enters the extension queue or desktop envelope.

Each incoming push is reduced immediately to bounded title/body text and exact TrackaLacker provenance, then written to a bounded `chrome.storage.local` queue before localhost delivery. CartCollect's `/trackalacker/push/signal` endpoint binds only to `127.0.0.1`, requires the pinned extension origin and paired companion token plus `Idempotency-Key`, records its mission decision before opening Chrome, and acknowledges ordinary business rejections such as no mission or over-cap price without retrying them. Exact transport replays remain idempotent. Equivalent product/store/event/price alerts inside the configurable five-minute window are deduped while an activation remains actionable, and simultaneous sources corroborate one purchase flow instead of opening duplicates. If live validation cancels that activation, a later signal on a new transport is eligible to activate it again.

The dashboard and tray show extension connectivity, subscription readiness, last-complete mapping count, queued alerts, recent decisions, occurrence counts, and measured median/p95 push-to-mission latency. **Recent TrackaLacker alerts** stays visible by default and records every delivered test, unsupported event, unresolved item, and exact match; only exact mapped store/item events continue into the actionable inbox or a mission. Once the bridge is Ready, choose **Verify browser test**, then click TrackaLacker's browser notification test button on the opened page. Cart Confirm waits for that real silent extension Web Push and confirms the full TrackaLacker → Chrome extension → desktop path; TrackaLacker's page-owned browser location supplies the single normal popup, and test notifications are always non-purchasing. **Pause delivery** keeps sanitized push signals queued in Chrome. **Run dry-run replay** tests only the local parser and resolver and can never open a store.

## Traffic overload behavior

The desktop opening queue and extension share the same safety goal: enter known drops promptly without turning normal monitoring into an unbounded reload storm. Manual and test openings use a fixed three-second stagger per store. Scheduled Walmart drops and their one exactly-once official-queue fan-out launch all applicable mission pages together, one initial page load per mission; ordinary automatic retries remain paced. Before a queue appears, each calendar-fired Walmart tab reloads only at the configured rapid lane and remains bounded by Stop, overload handling, the blitz window, and the fixed 120-action rolling-hour budget. Once a tab reports that it is queued, Cart Confirm stops refreshing it. Other participating tabs get only the configured final queue-capture reloads (zero by default, configurable from 0–20) and then stop. Tabless Target/Walmart watchers use independent randomized 45–90 second public-read deadlines; authenticated open-tab missions use the configurable watcher interval (60 seconds by default). Calendar-fired blitz tabs use the configurable pre-eligibility lane (two seconds per store by default); an eligible mission immediately leaves that stock-refresh lane. A product's fresh browser reservation replaces its own stale one so no product can starve the others, and main-frame navigations are observed so a retry cannot immediately follow a newly opened page. Retry notices and repeated observations stay out of Activity while each mission's status and last-checked time continue updating. Every browser opening and retry still consumes the unchanged fixed 120-action rolling-hour budget. Public quiet reads instead consume their independent 4,000/hour/store ledger; either lane waits when its own capacity or the shared retailer cooldown requires it.

Responses with status `429`, `502`, `503`, `504`, or `520`–`524` normally pause automatic navigation and store mutations for that retailer and propagate the same deadline back to pending openings. Main-frame failures always count; XHR failures count only in the bounded window after Cart Confirm authorized a store action, so unrelated retailer background polling cannot keep extending the cooldown. Multiple commerce XHR failures from one action are coalesced into one overload incident. Separate overload incidents exponentially increase the cooldown, decay after six quiet hours, and remain capped at 24 hours. Recognizable overload pages are reported as `traffic-overload` instead of being treated as out of stock; cooldown chatter remains on status surfaces and does not populate Activity unless an actual desktop notification is sent.

Calendar-fired Target purchase stages have one narrow exception for high-demand cart failures. During a durable, configurable per-stage burst (20 seconds by default), exact allowlisted Target Add, quantity, cart, checkout, and explicitly rejected final-submit actions may proceed through the overload deadline at a configurable cadence (750 ms by default). The burst caps each stage (16 Add, 12 quantity, 10 cart, 8 checkout, and 3 final-submit actions), still charges every action to the fixed 120/hour store budget, and stops immediately when the exact TCIN and configured quantity are verified. Unscheduled watcher missions use single actions at the watcher cadence and cannot reserve this overload bypass. An ambiguous final submission is never repeated; Target must explicitly state that the order was not placed before another fully revalidated submit.

The persistent 120-action rolling budget counts Cart Confirm's desktop page openings, automatic browser navigations, quantity changes, add-to-cart actions, cart transitions, checkout actions, and final submission attempts. The separate persistent public-monitor ledger counts every attempted quiet product-page GET, including failures, timeouts, and aborts; it never refunds or authorizes a browser/cart action. Neither ledger pretends to count every script/resource request made by a retailer page or traffic generated by other software.

This reduces traffic generated by Cart Confirm; it cannot prevent or measure traffic from other browser profiles, devices, users, extensions, or store-side demand. It also cannot make an already overloaded retailer available. The safe response is to wait, and the circuit does that.

## Privacy and local security

- The desktop server binds only to `127.0.0.1` on ports `32191` through `32195`.
- The extension and app use a random per-install token. The extension pins the first accepted token and rejects later mismatches; app and extension versions must match exactly.
- The unpacked extension has a deterministic ID. The local server requires a loopback `Host` header (defeating DNS rebinding) and accepts a request only when it carries that exact extension origin, or no origin at all together with the pinned extension-ID header — Chrome omits the `Origin` header on host-permitted extension requests, while readable cross-origin web requests always reveal their true origin and are rejected. All state-changing endpoints additionally require the per-install token.
- Settings, approved MSRP, and item profiles are stored under Electron's local user-data directory. `catalog.json` contains only the keyword, selected retailers and filters, normalized result identity/title/URL, displayed listing price when present, and timestamps. `trackalacker-import.json` contains normalized product/listing metadata and price-history summaries but no cookies or credentials. `msrp-research.json` contains cited suggestions and no credential.
- The optional OpenAI API key is not part of settings or research JSON. Like the Discord bot token, it is written to a separate file only after operating-system encryption succeeds; removing it deletes that encrypted file and disables scheduled research without deleting approved prices.
- The Discord bot token is not part of settings or runtime JSON. It is written to a separate file only after operating-system encryption succeeds; removing the saved token deletes that encrypted file.
- Reported page addresses are reduced to origin plus pathname; query strings are discarded.
- Admin-provisioned Howl source links and resolved retailer sharing URLs are an intentional exception to query-string removal: the admin-owned settings retain their affiliate parameters. The source and resolution metadata are excluded from both the renderer and Chrome purchasing configuration; the renderer receives only the validated retailer sharing URL needed for clipboard copy.
- A user-managed affiliate Open URL is stored separately after exact retailer/SKU validation and is also excluded from Chrome purchasing configuration. It is read only for the explicit mission **Open** action; automatic browser openings remain canonical.
- The bounded local ledger contains only milestone names, store/SKU, seller label, observed unit price and final total, quantity/attempt state, query-free paths, and timestamps.
- The app does not copy or store cookies, passwords, shipping addresses, payment details, CVV values, or order numbers.

## Troubleshooting

### Companion remains disconnected

Step 1 in the app diagnoses this: **Waiting for Chrome** means the extension has never reported in (load it, or click its reload arrow); **Reload the extension** means its version differs from the app; **Open a store tab** means the extension is loaded and the last requirement is a Target, Walmart, or Amazon tab in that Chrome profile — "Connected ✓" appears only once a store tab is reporting. The extension is named **Cart Confirm Companion** in Chrome's Extensions menu; Quick add is one of its toolbar actions.

Also check:

- Confirm Cart Confirm is running.
- Confirm the unpacked extension is enabled and reloaded after every update.
- Click the Cart Confirm toolbar icon in Chrome to force an immediate connection check.
- Reload a supported store tab in the same Chrome profile the extension is loaded in.
- Read the extension badge: `STOP` = connected and fully paused, `IDLE` = connected and observing while disarmed, `ARM` = connected and armed, `OFF` = Chrome cannot reach the app on `127.0.0.1` (app not running, or a firewall/antivirus is intercepting loopback), `UPD` = version mismatch, `PAIR` = pairing mismatch.
- The app opens product pages directly in Chrome when it can find it; if Chrome is not installed, pages fall back to the default browser, where the companion cannot see them.
- Close duplicate desktop app processes if ports `32191` through `32195` are occupied.

### Offer is blocked

Read the product status reason. Common causes are a third-party seller, seller text the store no longer exposes, a missing/changed price or final-total selector, a cap violation, quantity not offered, incomplete cart enumeration, or another item in the cart. Blocking is intentional when required evidence cannot be read.

### Store reports traffic overload

Leave the tab open and wait for the displayed workflow to cool down. Do not repeatedly reload it manually. A retailer-provided `Retry-After` can extend the configured cooldown, and each retailer has an independent circuit.

### Discord signals show `Needs attention`

Check the exact message in the Discord panel. `401` means the bot token was rejected; `403` means the bot cannot view the channel or read history; `404` usually means the copied channel ID is wrong or the bot is not in that server. Confirm Message Content access is enabled in the Developer Portal. A Discord rate limit is honored automatically. Changing channel IDs starts a new history baseline so old messages cannot auto-open.

### Walmart shows `/qp`

This is Walmart's official purchase queue. Leave the tab open. The first live queue signal in an Autopilot run sends one simultaneous initial navigation to every other enabled Walmart mission; already queued tabs are skipped, and a durable receipt prevents another fan-out during that run. Cart Confirm recognizes Walmart's structured `/qp` queue and product-route holding pages only when they contain explicit waiting-room evidence tied to the exact mission item. Generic high-traffic/error copy remains an overload instead of being guessed as a queue. Cart Confirm deliberately does not call embedded ticket URLs, replay signatures, force refreshes, or skip the queue. Automation resumes only after Walmart redirects an admitted tab to its product flow.

### Badge shows `UPD` or `PAIR`

`UPD` means the desktop app and unpacked extension versions differ. Version 2.9 and later include a one-shot automatic reload: after newer Cart Confirm files replace the files in the same unpacked-extension folder, the installed companion reloads those files by itself and records the transition so it cannot loop. Packaged installs receive both the app and that extension folder through the same checksum-verified Setup asset selected by **Check for updates**; the extension reload performs no separate download. Upgrading from 2.8 or older still needs one final manual reload because those versions do not contain the updater yet. Chrome Web Store or managed distribution would be required for completely unattended remote delivery, and Chrome may still require one approval when a release adds a permission.

`PAIR` means the locally pinned companion token changed. Verify that only the intended Cart Confirm process is running, then remove and load the unpacked extension again to establish a new first-use pairing.

### Store page changed

Retailer HTML and accessibility labels change frequently. Store-specific selectors live in `extension/retailers.js`. Keep automation disarmed while updating and testing an adapter.

### Security challenge is missing images

The companion disables fast-load blocking for ten minutes when it detects a challenge. Reload the page once if the challenge asset does not appear, complete it manually, and let the normal page continue.
